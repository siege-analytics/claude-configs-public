# Hub delivery decision (#1315)

## Evidence and finding

The operator observed repeated hub stops alongside steward stops. A live hub admitted that no instruction required its whole-goal stop: it generalized action-specific holds and over-prioritized gate management despite already-loaded finish-line guidance. After an operator challenge it prepared off-tree evidence but stopped with an unrun packet and no worker handoff; another operator instruction caused it to audit hold merit and route the packet to its existing writer and independent reviewer. These later tools are progress after prompting, not proof that autonomous persistence is fixed. An upstream coordinator had already directed eligible work to continue.

The shared strategic-agency:2 rule used advisory wording and left the after-result/stop decision implicit. Replace that paragraph with a concrete, imperative next-action decision and reference the existing session-coordination:9 protocol. Do not add copies to every hub/steward skill, a new ledger, all-owner ACKs, a universal permission exception or permanent foreground watching.

## Behavioral acceptance cases

1. A worker returns a complete artifact and the hub owns verification/PR delivery. Advance verification or delivery; receipt-only reporting is insufficient.
2. Deployment is held but authorized source evidence is independently eligible. Preserve the deployment hold and perform or assign that evidence work.
3. A diagnostic fails because a compound command included a real Git object write. Identify the actual secondary mutation, choose an adequate authorized read-only diagnostic or route a genuine scoped prerequisite; do not call the whole mission blocked or falsely classify the refusal as a read-only gate defect.
4. Required independent review is genuinely running. Verify the handle or current owner/event, keep other eligible work moving, and return at a finite host boundary when appropriate. A checkpoint without a supported continuation does not promise another automatic turn.
5. The finite assignment is complete or the role is review-only. Return its result/baton or completion honestly; do not manufacture implementation, unrelated tasks or endless monitoring.

These cases require independent decision review and actual subsequent hub follow-through without another operator nudge. Build and structural checks do not prove behavioral success. Treat an idle session with a genuinely completed finite assignment differently from a hub leaving owned eligible backlog untouched.

## Rollout and limits

Publish one maintained Core rule via feature→develop→main and normal flat consumer delivery. Inspect the actual loaded client hub doctrine; keep project-specific boundaries and replace generic duplicates with the shared reference during authorized cleanup. Do not reset the independent runtime correction #1314 to add this change. Do not interrupt a hub already doing useful work merely to apply a prompt.

The desired behavior is initiative within the existing mission and authority, not a promise that a language model can never stop incorrectly. Repeated behavior is observed after delivery before claiming this incident class fixed.
