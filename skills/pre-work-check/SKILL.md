# Pre-Work Check

Understand the requested outcome and current target. Read relevant existing task history, code and decisions. Identify real dependencies and role boundaries, then start eligible work within the grant.

An existing user request or operational task can supply the goal. Use an existing ticket when available; create or repair tracking when useful or required by the project policy. Missing board placement, an epic, a type label or a universal ticket destination is not itself a reason to stop authorized work.

An open upstream issue blocks only actions that actually depend on its result. Distinguish a material decision or required input from a merely related work item. Continue independent implementation, review or preparation and route concrete dependencies to their current owners.

Use [`think`](../think/SKILL.md) for proportionate preparation and host-required own-task scope. Use [`develop-guard`](../develop-guard/SKILL.md) for the project's approved branch path. Preserve genuine explicit holds and consequential operation approvals. Do not manufacture missing authorization from your own notes or repeat a refused effect through another actor.

Proceed once the next useful action and its authority are clear. Keep task status honest and verify outcomes through [`self-review`](../self-review/SKILL.md) and [`definition-of-done`](../_definition-of-done-rules.md).
