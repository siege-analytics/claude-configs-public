# Host controls and deployment navigation

Read this before repairing or replacing a session. It adds no authority, gate or permission setting. Use [rule:autonomy], [rule:standing-approval] and [rule:tandem-agent] for authorized continuation, readiness and assigned roles. Preserve explicit owner holds; hold only their dependent actions.

## Establish what the host can do

Inspect the tools and documentation exposed in the current runtime. Identify supported session status, messages, configuration, pause/interruption, resume and retirement controls. Do not infer that a control exists from another host's instructions, or that it is absent from an old incident. A tool name in an artifact is not proof of availability. Access is not authority to change a model, permissions, settings or another session's work.

Inspect the actual session and latest substantive reply, then any live tool handle or process on which the next decision depends. A recent log timestamp alone does not prove useful progress; an observation timeout does not prove termination. Re-poll the same handle or inspect another authoritative status source. Do not start a duplicate operation because observation expired.

## Choose and observe a bounded repair

- For a supported, authorized in-place configuration or retry correction, inspect the failing predicate, change only the required setting or request, and observe a real successful response. Do not retry an unchanged persistent failure.
- For a live wedged operation, inspect incomplete mutations before using a supported pause or interruption control. Observe whether the operation actually stopped. Reconcile durable state before resuming; an interruption can leave a partial write.
- When a necessary control is unavailable or fails, name the capability or operation that remains unresolved. Preserve the recovery checkpoint and perform independent authorized work. Do not label an observation failure as a stopped process.
- Before a successor writes, check for an existing healthy owner, settle concurrent ownership and carry forward the actual objective, evidence, pending operations and holds. The main recovery procedure owns that handoff and retirement sequence. Journal supersession alone cannot stop a predecessor's tools.

## Source, installation and verification have different owners

KERNEL K5 owns the Siege scaffold's develop-to-main publication and exact current remote-main installation boundary. A source branch, successful test or released archive is not installed-runtime proof. Use [skill:develop-guard], [skill:merge] and [rule:writing-releases] for their existing procedures. Other consumers retain their separately approved topology and delivery mechanism; a generic recovery note does not authorize replacing project policy or held files.

For the scaffold source, README's local-validation instructions and `bin/validate-local.py --help` own supported commands. Preview with `python3 bin/validate-local.py --list` in an isolated source worktree. Full mode runs local CI steps; it does not publish or install, and its preflight does not replace required server checks. Use the supported interpreter and pinned validation dependencies rather than changing global tool configuration to make a check pass.

For Craft deployment, inspect the actual canonical source's `bin/sync-workspace-hooks.sh --help`, Craft enforcement documentation and installer/verifier instructions. Verify the explicit target, source identity and existing project deployment mechanism before mutation. Preserve operator settings, unknown hooks, session/task evidence, owner holds and rollback inputs. A consumer with its own reviewed import or deployment path continues through that path.

After normal installation, verify managed-source identity and preservation separately from a real native session action. Confirm required positive and negative behavior through the host that uses the hooks. Local Git probes, package checks and source review do not establish a live Craft callback. If Craft cannot submit a prompt, use an external terminal for diagnostics and the normal canonical installer; do not fabricate task evidence or disable a guard to turn a failed recovery into a passing report.
