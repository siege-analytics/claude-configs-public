# Self-review: self-verifying enforcement harmonisation (#96)

## Assumptions

- Craft Agent cannot deny a tool call through `automations.json` (only `prompt`
  and `webhook` actions exist), so CA hard-blocking runs through the SDK
  `UserPromptSubmit` `continue:false` command hook (`ca-enforcement-gate.sh`)
  and native git `pre-push`. Verified against `docs/automations.md` and #416.
- `build.py --deploy` already produces the bundle, `CLAUDE.md` symlink,
  manifest, and native git hook. The gap is wiring the blocking wrapper and the
  watchdog automation, and proving liveness. Verified by reading
  `deploy_to_workspace()`.

## Pre-author inventory (applying authoring-against-state to this work)

### Inputs read
- `bin/install.sh`, `bin/install-hooks.sh`, `bin/build.py`
  (`deploy_to_workspace`, `_merge_ca_enforcement_settings`, `build_ca_enforcement`,
  `build_consumer_packages`, `main`).
- `hooks/resolver/ca-enforcement-gate.sh`, `hooks/settings-snippet.json`,
  `craft-agent/automations-snippet.json`, `craft-agent/standing-order-watchdog.json`.
- `.github/workflows/*.yml` (CI gates), `hooks/_test/*`, `CONTRIBUTING.md`.

### Contact-point measurements
- Ordering defect: `deploy_to_workspace()` merges the wrapper only
  `if settings_dst.exists()`; `install.sh` runs `--deploy` before
  `install-hooks.sh` creates that file, and `install-hooks.sh` overwrites it.
  Confirmed empirically: a fresh synthetic workspace shows 0
  `ca-enforcement-gate` registrations before wiring, 1 after.
- Watchdog automation is never registered by any code path. Confirmed by grep
  (`automations-snippet` referenced only in `build_consumer_packages` copy, not
  in deploy).

### Hypothesis (what the code implements)
- A standalone idempotent `bin/wire-enforcement.py` that merges the blocking
  wrapper (last-writer, after `install-hooks.sh`) and registers the watchdog.
- A reusable `bin/verify-enforcement.sh` that runs a live block test plus wiring
  assertions and exits non-zero when advisory-only.
- `install.sh` runs wiring then verify; enforcement gaps become hard failures.
- `bin/harmonize.sh` as the idempotent recurring entrypoint.

## Peer review (mechanics, correctness, craft floor)

- Idempotency proven: two consecutive wire runs leave exactly one wrapper
  registration and one watchdog entry.
- Safety proven: a seeded pre-existing consumer automation (the electinfo sync
  job) is preserved exactly once; the merge writes a timestamped backup and
  restores it if the result does not parse.
- Live block test proven: the probe drives the deployed gate with a mock
  STALE-DESIGN think-gate and asserts `continue:false`.
- Negative case proven: a skills-only workspace fails the probe (rc=1), which is
  precisely the production failure this change targets.
- New test `hooks/_test/verify_enforcement.test.sh` passes (3/3).
- CI-equivalent gates pass locally: `build.py --check`, `build.py`,
  `sync-skill-references --check`, `validate-hooks.py` (repo + craft-agent),
  `scripts/ci/test_flat_skill_layout.sh`.

## Lead review (approach-fit, blast radius, sequencing)

- Blast radius contained to the Craft Agent install path plus additive scripts.
  Direct-clone (Claude Code) install behaviour is unchanged. `build.py` is not
  modified; the wiring lives in a standalone script.
- Highest-risk step is the `automations.json` merge against a live consumer
  file. Mitigated by replace-by-name (never delete), post-write JSON validation,
  backup-and-restore on parse failure, and a probe assertion.
- Known cosmetic drift left out of scope: `build.py` still sets a dead
  `CLAUDE_CA_ENFORCE` env (removed as a gate in #572). Harmless; noted for a
  follow-up so this PR stays scoped.
- CHANGELOG.md and README.md additions were prepared but held out of the commit
  because this session can only push to siege-analytics through the file API
  (bot-cred git push is denied), which cannot safely re-emit the 100KB+
  CHANGELOG. They are quoted in the PR body for a maintainer follow-up.

## Evidence-predates-work
